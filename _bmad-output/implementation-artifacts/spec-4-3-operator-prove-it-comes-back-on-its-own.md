## Intent

**Problem:** Epic 4 ends only when recovery has been *demonstrated* rather than assumed, and nothing has been demonstrated: `launchctl list` knows no `ai.mastra.*` job, `~/Library/Logs/mastra-factory/` does not exist, and Story 4.2 is still parked awaiting its operator. `ops/README.md` teaches how to bring the agents up and how to check that they are up, but it says nothing about how to *break* the deployment on purpose and watch it return — and the one recovery fact this host's disk encryption forces (an unplanned reboot has no session, no agents and no remote access until a human authenticates at the pre-boot screen) is recorded in `docs/Self-hosting research.md` §7.5 and in the spec, not in the ops subject's own normative document.

**Approach:** Every proof is an action on the host — a `launchctl kickstart`, a real logout and login, a deliberate out-of-order bootstrap, a forced `newsyslog` run — so this story commits the *procedure and its readings* rather than performing them: a numbered `## Recovery proofs` section and a `## Recovery limits` section in `ops/README.md`, one gate guard keeping the job names those commands address from drifting away from the plists, and a non-empty `operator_actions:` list. Then it parks at `awaiting-operator`.

## Boundaries & Constraints

**Always:**

## Design Notes

**Why the wait branch is forced rather than waited for.** The honest way to see `ops/factory-start.sh`'s wait is to create the condition it exists for: `bootout` both agents, `colima stop`, bootstrap **Factory first**, read the line out of `out.log`, then bootstrap Colima and watch `[factory] docker socket is up — starting the server` follow. Hoping to catch it during an ordinary login is a race that usually resolves the other way, and its absence then proves nothing — which is exactly the ambiguity supervision checkpoint 3 already has to hedge against. Forcing it also exercises the branch's *exit* path, since a Colima that is never bootstrapped ends in the ten-minute `err.log` diagnostic rather than a crash-loop.

**Why forced rotation takes a file argument.** `sudo newsyslog -F -v` alone forces a trim of every log named by `/etc/newsyslog.conf` and everything in `/etc/newsyslog.d/` — the host's own logs included. `man newsyslog` records that a trailing file argument restricts the run to matching logs, so `sudo newsyslog -F -v /Users/koval/Library/Logs/mastra-factory/out.log` proves the *installed* conf (the file is found through it) while touching one log. Passing `-f ops/newsyslog/ai.mastra.factory.conf` instead would prove the repo copy, which is not what rotates at 3 a.m.

**Why proof 4 has two passing readings.** "The artifacts" already records that macOS `newsyslog` rotates by rename with no copy-truncate and that `N` means no process to signal, while launchd holds the descriptor it opened at spawn. So the live log either keeps being written or does not, and both are results — the second is the known limit confirmed on this host, cured by `launchctl kickstart -k`, which also reclaims the disk the unlinked inode was holding. Writing the proof to demand only the first outcome would turn a documented limit into a failed step and invite an operator to go looking for a fault that is not there; what the proof requires either way is that the compressed generation exists and that the outcome gets recorded.

**Why the planned restart is proof 5 and optional.** The epic's four acceptance criteria are proofs 1-4; the epic *goal* also says the deployment survives a planned restart, and `sudo fdesetup authrestart` is the only path that does under FileVault. `fdesetup supportsauthrestart` answers `true` on this host, but the man page notes the command "may not work on all systems", and a restart is a far larger interruption than the other four. So it is written as the recommended last proof rather than a gate, and its result feeds `## Recovery limits`.
