01 The whole line, end to end

Three commands start work, four answer a stopped line, two clean up after it. Nothing else is required to operate the loop.

02 What is legal after what

A run has five states. Most commands are only accepted in one of them — that is the whole grammar.

CommandLegal whenWhat it leaves you in / what follows
validateany timeRead-only preflight. Non-zero exit means run will not work yet.
run --dry-runany timePrints the dispatch plan, spawns nothing. Always the step before run.
runno live run→ LIVE. Accepts --epic, --story, --max-stories, --spec.
list · lsany timeRun ids and short refs — where you get the RUN_ID every other command wants.
status [id]any timeRun + sprint state. --json for scripting.
tuiany timeLive dashboard. Cheaper than polling status.
attach [id]live onlytmux into the agent session. Detach with Ctrl-b d — do not kill the pane.
stop --gracefullive only→ STOPPED (resumable). Also suppresses pending auto-sweeps.
stoplive only→ STOPPED (hard). Next run/sweep reconciles leaked worktrees.
stop --cancel-gracefulgraceful pendingWithdraws the request; the run keeps going.
resume RUN_IDpaused / stopped clean→ LIVE, from the same point.
resolve RUN_IDCRITICAL onlyDisambiguates the spec, re-arms, then prompts to resume. --no-interactive if you already fixed it by hand.
confirm --listany timeWhich stories are parked and what each one owes you.
confirm STORY_KEYstory parkedCompletes it. Independent of whether a run is live. --reverify re-runs the verify gate first.
decisionssweep left questionsAnswers triage questions a sweep could not settle alone.
sweepno live runWorks the deferred-work ledger. auto = never here, so it is always your call.
diagnose [id]any timeSanitized dump to hand to maintainers. Never mutates the run.
cleanupterminal runsKills leftover tmux sessions and windows.
cleanterminal runsReclaims disk. Paused runs are never touched, so they stay resumable.
archive RUN_IDterminal runsCompresses into .bmad-loop/archive. --force stops a live run first.
delete RUN_IDterminal runsRemoves the run directory. Progress survives — it lives in git and sprint-status.yaml.

Rule of thumb: green commands are read-only and never wrong to run. Blue ones need a live run, amber ones need something waiting on you, and grey ones need the run to be over.

04 When a lamp lights

A desktop notification fires and an ATTENTION file lands in .bmad-loop/runs/<run-id>/. One status call tells you which of five things happened.

Epic gate

The normal checkpoint

Fires after the last story of an epic commits, because gates = "per-epic". Read the diff, then release the line.

git log --oneline main bmad-loop resume RUN_ID
CRITICAL escalation

The spec is wrong

Dev and review found a gap or a contradiction neither can safely settle — including review writing a story back off done.

bmad-loop resolve RUN_ID # or, spec fixed by hand: bmad-loop resolve RUN_ID --no-interactive
awaiting-operator

Code is done, the world is not

The story shipped and committed, but its criteria need a human: start Docker, publish DNS, grant a key. Several stories here are shaped exactly this way.

bmad-loop confirm --list bmad-loop confirm STORY_KEY --reverify
Deferred work

The ledger, on your schedule

sweep.auto = "never", so nothing is swept behind your back. Work it between runs.

bmad-loop sweep --dry-run bmad-loop sweep --min-severity high bmad-loop decisions

05 Muscle memory

Two chains cover almost every session. Learn these and read the tables only when something unusual happens.

Starting a shift

  1. bmad-loop validate — is the bench clean?
  2. bmad-loop run --epic 1 --dry-run — is the plan right?
  3. bmad-loop run --epic 1 — start the line
  4. bmad-loop tui — second terminal, watch it
  5. bmad-loop resume RUN_ID — at the gate

Ending a shift

  1. bmad-loop stop RUN_ID --graceful — finish the story first
  2. bmad-loop status RUN_ID — confirm it landed
  3. bmad-loop resume RUN_ID — tomorrow, same point
  4. bmad-loop confirm --list — clear anything parked
  5. bmad-loop cleanup && bmad-loop clean — once finished

One thing this board cannot show you: session_budget_mode = "warn" means a runaway session gets a notification but is not killed at the 4M-token cap. Before leaving the line unattended overnight, consider setting it to "enforce".
